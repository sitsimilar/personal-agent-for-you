## 二、问题清单

> 已修复项不再重复列改进建议，统一在第三节「与上期对比」呈现。本节聚焦本期仍遗留的问题。

### 问题 1：`.host` 旧域名站点「检查更新」因 CORS 跨域静默失败（上期问题 2 的遗留，未修复）

- **问题描述**：本次实测登录页、首页、全部信息、待办、思维树、回顾、工具箱、设置、回收站**所有页面**均持续抛出 `Access to fetch at 'https://personal-agent-08495.app.workbuddy.link/version.json' from origin 'https://personal-agent-08495.app.workbuddy.host' has been blocked by CORS policy`。经源码复核确认：`shared/config/version.ts` 的 `UPDATE_SOURCE_URL = ${publicConfig.endpoint}/version.json`，`publicConfig.endpoint` 来自构建时注入的 `VITE_CLOUD_ENDPOINT`（本地 `web/.env` 已切 `.link`），因此 `.host` 域名上仍部署着「域名切换后」构建的产物（JS 内 endpoint 已指向 `.link`），但 `.host` 域名本身仍对外服务（`curl .host/version.json` 与 `.link/version.json` 均返回 200）。页面运行时向 `.link` 发起跨域请求，被 CORS 策略拦截，导致「检查更新」功能静默失效（当前版本号 v2.13.0 仍能正常显示，因其为构建时注入常量）。
- **影响程度**：中
- **改进建议**：
  1. **首要**：确认正式域名已统一为 `.link`，让 `.host` 旧域名停止对外服务（下线或 301 永久重定向到 `.link`），避免用户停留在旧域名上遇到各类跨域/资源异常；
  2. **兜底**：`version.json` 请求改为「同源相对路径」（`/version.json`）而非依赖 `endpoint` 拼接，从根本上消除跨域；或由部署层 `server.js` 在返回 `version.json` 时显式补充 `Access-Control-Allow-Origin` 头；
  3. 评估脚本 `qa/ux-walkthrough.cjs` / `qa/ux-mindtree.cjs` 中的 `BASE` 常量应同步切换到正式域名 `.link`，避免长期针对旧域名走查得出误导性结论。
- **优先级**：P1 —— 虽然正式域名已切 `.link`，但只要 `.host` 仍可访问，任何通过旧链接/旧收藏/旧分享进入的用户都会遇到更新检测失效，且同源跨域问题可能波及其它依赖 `endpoint` 的请求；属于「域名切换未收尾」的线上卫生问题，应尽快收口。
- **预期改进效果**：旧域名不再产生跨域报错；更新检测在任意入口下均可正常工作；评估基线回归真实线上域名。

### 问题 2：会话失效拦截建议用「真实过期 token」补充验证（上期问题 4 的遗留，未落地）

- **问题描述**：源码层面会话失效链路完整（`main.tsx` 注册 `setUnwrapAuthHook(onServiceError)` → `unwrap` 抛错前回调 → `isAuthExpired` 识别 → `reportAuthExpired` 清会话跳登录 → `LoginPage` 消费回跳路径）。但本次评估注入的测试会话仍使用伪 token（`ux-eval-fake-token-not-real`），实测各云端页面命中 401 后页面仍显示「操作失败，请稍后重试」并**未触发跳转登录**。这可能是评估脚本伪 token 触发的 401 错误结构与真实 SDK 返回结构不一致所致，但存在「真实 token 过期场景拦截未生效」的回归风险，无法仅凭源码断言。
- **影响程度**：中（潜在）
- **改进建议**：补充一次「真实登录 → 手动使 token 失效（或等待过期）→ 刷新页面」的端到端验证，确认 `isAuthExpired` 能正确识别真实 SDK 的 401 结构并触发跳转；若未触发，则补齐对应错误字段到 `isAuthExpired` 的识别分支。
- **优先级**：P2 —— 会话失效是必现场景，但该链路已历经多期源码复核确认完整，且未收到真实用户反馈，属「验证方法缺口」而非「疑似缺陷」，优先级较上期的 P1 下调一档。
- **预期改进效果**：确认会话过期时用户一步完成重登并回到原操作现场，彻底消除「软件坏了」类困惑。

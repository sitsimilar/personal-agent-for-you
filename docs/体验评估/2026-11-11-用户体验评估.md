## 二、问题清单

### 问题 1：评估脚本登录页 a3/a4 步骤 strict mode 误匹配（上期问题 1 遗留，未修复）

- **问题描述**：`qa/ux-walkthrough.cjs` 登录页 A3「未取码直接点登录」、A4「未取码填任意验证码再登录」两步，仍使用 `getByRole('button', { name: /登录/ })` 定位登录按钮。因按钮文案为「登录 / 注册」（`LoginPage.tsx` 第 174 行），而「微信扫码登录」按钮（第 180 行）accessible name 同样含「登录」，正则 `/登录/` 同时命中 2 个按钮，触发 Playwright strict mode violation，`.click()` 被 `.catch(() => {})` 静默吞掉——**登录按钮实际从未被点击**，`submit()` 未执行。据此，本期 `ux-report.json` 中 `a3_loginNoCode`、`a4_wrongCode` 仍仅捕获到「验证码 / 获取验证码」标签、无任何校验文案，实为脚本静默失败所致，并非产品缺陷。产品侧校验逻辑（`LoginPage.tsx` `submit()`：无 pending →「请先获取当前手机号的验证码」；空 code →「请输入验证码」）源码复核无 bug。
- **影响程度**：低（仅影响评估覆盖完整性，不影响真实用户）
- **改进建议**：
  1. 脚本将 `getByRole('button', { name: /登录/ })` 改为 `getByRole('button', { name: '登录 / 注册', exact: true })`（或 `{ name: /^登录 \/ 注册$/ }`），消除与「微信扫码登录」的歧义；
  2. 去掉 `.click().catch(() => {})` 的静默吞错，改为显式断言点击成功（否则 strict mode 失败会被永久掩盖）；
  3. 补充 `a4_wrongCode` 的真正校验语义：当前 A4 因从未取码，`pending` 恒为 null，实际命中的仍是「请先获取当前手机号的验证码」而非「请输入验证码」；如需覆盖「错误验证码」路径，应在 A4 前先真实触发一次 `sendPhoneCode`（或 mock `pending` 状态）。
- **优先级**：P3 —— 属测试基建质量，不影响线上用户；但长期会掩盖登录校验回归，建议随下期评估一并修正。
- **预期改进效果**：登录页「未取码」「错误验证码」两条校验路径被真实覆盖，评估结果可信；消除 strict mode 静默失败隐患。

### 问题 2：会话失效拦截建议用「真实过期 token」补充验证（上期问题 2 遗留，未落地）

- **问题描述**：源码层面会话失效链路完整（`main.tsx` 注册 `setUnwrapAuthHook(onServiceError)` → `unwrap` 抛错前回调 → `isAuthExpired` 识别 → `reportAuthExpired` 清会话跳登录 → `LoginPage` 消费回跳路径）。但本次评估注入的测试会话仍使用伪 token（`ux-eval-fake-token-not-real`），实测各云端页面命中 401 后页面仍显示「操作失败，请稍后重试」并**未触发跳转登录**。这可能是评估脚本伪 token 触发的 401 错误结构与真实 SDK 返回结构不一致所致，但存在「真实 token 过期场景拦截未生效」的回归风险，无法仅凭源码断言。
- **影响程度**：中（潜在）
- **改进建议**：补充一次「真实登录 → 手动使 token 失效（或等待过期）→ 刷新页面」的端到端验证，确认 `isAuthExpired` 能正确识别真实 SDK 的 401 结构并触发跳转；若未触发，则补齐对应错误字段到 `isAuthExpired` 的识别分支。
- **优先级**：P2 —— 会话失效是必现场景，但该链路已历经多期源码复核确认完整，且未收到真实用户反馈，属「验证方法缺口」而非「疑似缺陷」。
- **预期改进效果**：确认会话过期时用户一步完成重登并回到原操作现场，彻底消除「软件坏了」类困惑。

### 问题 3（维持）：线上 `.host` 站点仍为 v2.13.1，本地 v2.13.2 未提交、未发布（发布收尾观察）

- **影响程度**：低（线上功能完整可用，仅版本号与本地代码不同步，用户无感知）
- **改进建议**：按既定发版流程（先 `git commit` 落地 v2.13.2 改动 → 构建 web + 发布 → 同步版本说明）将 v2.13.2 发布到线上，使 `/version.json` 与三处 package.json、版本说明三处对齐；发布后下期评估基线即为 v2.13.2。
- **优先级**：P3 —— 不影响线上功能正确性，属发布节奏与版本一致性收尾，宜在近期发版时一并处理。
- **预期改进效果**：线上版本号与代码库、版本说明一致，「检查更新」显示真实版本，避免后续评估与用户感知的版本混乱。

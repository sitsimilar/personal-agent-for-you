## 1. 分层：哪些是纯函数，哪些碰浏览器

| 层 | 文件 | 依赖 | 可测性 |
| --- | --- | --- | --- |
| 像素 | `gray.ts` | 无 | Node 单测 |
| 特征 | `features.ts` | `gray` | Node 单测 |
| 分类 / 质检 / 计划 | `classify.ts`、`quality.ts`、`plan.ts` | `features` | Node 单测 |
| 感知哈希 | `phash.ts` | `features` | Node 单测 |
| 提示词 / 结果解析 | `prompt.ts`、`result.ts` | 仅 `types` | Node 单测 |
| 编解码 | `codec.ts` | `canvas`、`createImageBitmap` | 浏览器探针 |
| 编排 | `pipeline.ts` | 上面全部 | 浏览器探针 |

只有最下面两层碰浏览器 API。**阈值、打分、契约全在纯函数层**，所以能在 Node 里跑 1193 条断言，不用起浏览器。

## 2. 识别能力

### 2.1 场景 / 类别（11 类）

`code` 代码 · `error` 报错 · `ui` 界面 · `chat` 对话 · `table` 表格 · `chart` 图表 · `document` 文档 · `diagram` 示意图 · `photo` 照片 · `handwriting` 手写 · `unknown` 未判定

判定方式是**可解释加权证据**，不是黑盒：每类由 3~6 条排版信号（行距规律、横/竖最长直线、满版度、色相分散度、亮度双峰性、颜色种类…）线性打分，输出 `scores` 全表 + `margin`。`margin < 0.06` 时标 `uncertain`，界面提示"可手动改类别"。

模型可以**覆盖**这个前置判断（结果里的 `scene` 字段），分类只负责"先问哪套清单"。

### 2.2 输入条件

| 条件 | 支持情况 |
| --- | --- |
| 多图 | 一次 ≤5 张，串行处理（并发 5 张 4K 会瞬时吃掉数百 MB） |
| 导入方式 | 文件选择、拖拽、`Ctrl+V` 粘贴 |
| 格式 | JPEG/PNG/WebP/GIF/BMP/TIFF/AVIF/HEIC/SVG —— 按**魔数**嗅探，不信扩展名 |
| 透明 PNG | 按白底合成（不合成会出现黑底假象，影响亮度统计） |
| EXIF 方向 | `createImageBitmap({ imageOrientation: 'from-image' })` |
| 超大图 | 长边压到 1600 / 1440 / 1280（按场景），先分步减半再缩，避免一次性重采样失真 |
| 超体积 | 硬预算 1.5MB/张、4MB/批，超了走体积阶梯（见 §3.3） |
| 重复图 | 批内感知哈希去重（`SAME_IMAGE_DISTANCE = 10`） |
| 单张失败 | 只跳过这一张，其余照常送；全失败才报错 |

### 2.3 预检徽标

上传后、点分析之前，界面就展示每张图的「场景 / 质量 / 压缩后体积」，用户能先看到"这张糊了"再决定要不要重拍。

## 3. 算法改动前后对比

### 3.1 速度（Node 24，median of 5，`bench-node-2026-11-14.json`）

| 尺寸 | 旧预处理 | 新预处理 | 提速 | 旧版哈希额外开销 | 端到端（特征+哈希+分类） |
| --- | --- | --- | --- | --- | --- |
| 1280×720 | 13.91 ms | 12.37 ms | 1.12× | 8.92 ms | 33.63 ms |
| 1920×1080 | 28.26 ms | 8.62 ms | **3.28×** | 19.68 ms | 26.06 ms |
| 3840×2160 | 102.96 ms | 13.28 ms | **7.75×** | 85.72 ms | 36.24 ms |

边界输入：空白 1920×1080 **16.62 ms**；长图 300×6000 **5.11 ms**。

改动点：

1. **不再"整图转灰度再缩"**。旧实现把 4K 的 830 万像素全量转成 `Float32Array`（33MB 分配 + 写），所以 4K 是 720p 的 6 倍；现在直接在 RGBA 上分块采样到 480 长边（每目标像素最多 3×3 样本并取均值），单次 O(目标像素)。**4K/720p 比从 7.2× 收敛到 1.08×**。
2. **哈希复用特征层的灰度图**。旧版为算 phash 又整图转一次灰度，4K 白付 85.72 ms。
3. **内容包围盒、颜色统计改在小图上算**，再按缩放比换算回原图（精度损失 ±8px，被 2% 边距吸收）。

### 3.2 精度

分类（`qa/vision-probe.ts`，11 个合成样本）：

| 阶段 | 结果 |
| --- | --- |
| 规则初版 | 7 个样本里只对 **3** 个（界面→表格、照片→图表、报错弹窗→文档、深灰编辑器不判暗底） |
| 现在 | **11/11 合规**（`terminal-red` 允许 `code\|error`，实测 `code`） |

关键修正（按影响排序）：

- **横/竖最长直线分离**：`axisRatio` 取横竖最大值时，"一条顶栏"的界面和"满屏网格"的表格同分 → 拆成 `axisH`/`axisV`，表格改用 `axisMin`（横竖都长才算表格）。
- **满版度 `inkRowCoverage`**：文档是"满版文字"（0.4~0.6），弹窗/界面只有零星几行（0.1~0.2）——这是把"一页文档"和"一个提示框"分开最省算力的信号，配合 `docGate` 软门（深底压分而不是写死排除）。
- **颜色种类归一区间**：`distinctColorRatio` 的真实量级是 0.001~0.08（不是 0.02~0.5），区间错了会让照片永远拿不到分 → 照片被判成图表。
- **色相分散度 `hueSpread`**：照片红/橙/蓝/绿都有（0.6~0.8），截图往往只有"一个主题色 + 灰"（0.1~0.3）。

质检（`quality.ts`）：

| 问题 | 改前 | 改后 |
| --- | --- | --- |
| 眩光误报 | **所有白底截图**都报 `glare`（"大面积高亮像素"），误报率 100% | 眩光只在 `photo/handwriting/unknown` 判；截图本来就有大片 255 |
| 低对比误报 | 界面被判 `low_contrast` | 需同时满足 `edgeDensity > 0.05`（真有笔画的低对比才算） |
| 纯色图 | 全白图靠"缺席证据"拿 0.5 假高分，被判文档 | 先拦：`edgeDensity < 0.004 && stdLuma < 6` → `unknown` |
| 4K 判糊 | 在缩略图上算锐度，4K 必糊 | 在原图 3 块 256² 补丁上取中位拉普拉斯方差 |

### 3.3 稳定性

- **体积阶梯**（旧版最大的坑：4000×3000 PNG 转 dataURL 超 5MB，请求 body 顶到网关上限，表现成"偶发识别失败"）：

  `PNG → WebP q0.9 → JPEG q0.8 → JPEG q0.65 → 像素 0.6× → 放弃`，5 次让步 + 首次 = `MAX_ENCODE_ATTEMPTS 6`，**先牺牲画质、再换编码器、最后牺牲分辨率**；仍压不进预算时照送但 UI 标"体积告警"，不阻断。

- **错误四分类**：网络/限流（可重试）、鉴权、模型不可用、输入不可用（重试无意义）。只有可重试类重试 **1** 次，延迟 900ms。
- **解析永不抛错**：`parseVisionResult` 逐字段 narrow，字段类型不对就丢该字段，全盘不合法则 `structured=false` 退化成纯文本展示；模型自评 `ok` 但缺字段过半时降为 `partial`（避免"看起来成功其实没读到"）。
- **JSON 修复**：模型返回带注释/尾逗号的 JSON 时，走一次 `buildJsonRepairPrompt` **只修格式**，不重解问题。
- **缓存**：FNV-1a key + localStorage，24h / 20 条，`schemaVersion` 参与 key，结构变了旧缓存自动失效。

### 3.4 真实浏览器探针：本轮发现并修掉的两个缺陷

Node 里没有 JPEG/WebP 编码器，所以体积压缩率、编码耗时、以及**预处理是否真的按计划执行**只能在浏览器里量。`qa/vision-browser-probe.mjs` 用 esbuild 打包生产管线 → 无头 Edge（CDP 驱动）→ 生成 3 张合成截图跑完整 `prepareVisionInput`。跑第一遍就抓到两个 Node 单测覆盖不到的缺陷：

**缺陷 1：坐标系污染，界面图被裁掉 98%（严重）**

`pipeline` 交给特征层的是 512 长边的**工作副本**，而 `scaleToOriginal` 用"工作副本宽 / 分析图宽"算 → 得到 1.067（正确值 5.333）。于是 `contentBox` 是 512 空间的坐标（340×258），却被 `planPreprocess` 当成原图坐标去裁 2560×1440 的图。

结果：2560×1440 的界面 → 裁成 340×258 → 文字全糊，只剩 2% 面积，而所有单测都是绿的（单测里"位图就是原图"，天然绕过了这个分支）。

修复：

- `extractFeatures(img, { sourceWidth, sourceHeight })` 显式接收原图尺寸，`scaleToOriginal` 按它算；
- `contentBBox` 换回原图坐标后夹到图内（避免 1px 溢出黑边）；
- `planPreprocess` 加双保险：`MIN_CROP_KEEP = 0.35`（检测框覆盖 <35% 不裁）、`MIN_CROP_SIDE = 0.4`（细长条不裁）—— 因为包围盒是在 480 长边上算的，细笔画可能被采样漏掉，**宁可少裁（多送点白）也不能误裁（信息直接丢）**；
- 顺带修好 `lineHeightPx`：原来被低估 8 倍（4K 的 5 行间距被当成 0.6 行高），"小字 2× 放大"规则等于失效。

回归用例 3 条（`contentBox 按原图坐标返回`、`检测框过小不裁`、`细长条框不裁`）。

**缺陷 2：橙色被当成红色，暖色照片判成"满屏报错"**

旧判据 `r > 110 && r-g > 40 && r-b > 30` 把橙色也算红。一张日落渐变（深蓝→橙→浅黄）`redRatio = 0.7966` → `error 0.815 > photo 0.625`，被判成报错。

修复（三处，都可独立解释）：

1. **只认"真红"**：色相落在 345°~15°、饱和 ≥0.5、且 `r-g`/`r-b` ≥60。`#c06c4a`（hue 17.3°）被排除，告警条/危险按钮（hue≈0）仍算。
2. **红色归一区间 0.2%~3% → 1%~12%**：报错截图的红是**成片**的（告警条 + 危险按钮 ≥10%），旧区间下"角落一个红图标"也拿满分。
3. **照片加 `hueSpread`、报错加 `0.06×(1-cover)`**：暖色渐变的颜色种类可能很少（量化后只有几十个桶，`distinct` 仅 0.005），但它色相分散；报错弹窗通常不满版。

改后：同一张图 `redRatio 0.7966 → 0.0671`，判 `photo 0.774`。报错弹窗仍 `error 0.763`（margin 0.091，置信）。

### 3.5 体积与编码（真实浏览器，`encode-probe-2026-11-14.json`）

| 样本 | 原图 | 原体积 | 送入尺寸 | 送入体积 | 压缩到 | 编码 | 预处理 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 代码 4K | 3840×2160 | 1415 KB | 1600×900 | 738 KB | 52.2% | PNG | 244 ms |
| 界面 2K | 2560×1440 | 76 KB | 1600×1214 | 44 KB | 57.8% | PNG | 115 ms |
| 照片 12MP | 3024×4032 | 25.2 MB | 960×1280 | 97 KB | **0.4%** | WebP q0.9 | 770 ms |

照片那 770ms 几乎全花在**解码 25MB 源码级 PNG**上（真实场景是 3~4MB JPEG，约 200ms）。文字类用 PNG 保笔画，其余用 WebP。

## 4. 图 + 代码联合解题

### 4.1 输入

| 输入 | 说明 |
| --- | --- |
| 图片 ≤5 张 | 走 §2 的预处理，图按「图1、图2…」编号 |
| 代码 | 可选，最多 12000 字符（超了截断并在提示词里声明截断位置） |
| 上下文 | 用户补充的自然语言（"点保存后就这样"、"只在 Windows 复现"） |
| 场景 | 自动判定，可手动改 |

### 4.2 输出契约（`VisionResult`，`schemaVersion: 2`）

```
status        : ok | partial | failed        模型自评
coverage      : { expected, missing[], unreadable[], ratio }   读没读全
blocks[]      : { type, order, text, rows, cols }              分块转写
understanding : { summary, evidence[], transcribed[] }         ① 输入理解
localization  : { file, line, symbol, reason, confidence }     ② 问题定位
solution      : { steps[], patch, verification[], boundaries[] } ③ 解决方案
needMoreInfo  : string[]                                       还缺什么
raw           : 原文（structured=false 时兜底展示）
```

三段式是**硬约束**，写进 `OUTPUT_SCHEMA` 的 JSON 契约里，不是提示词里的一句建议：

- **① 输入理解**：`evidence` 必须能在图里或用户代码里逐条指认（禁止编造），`transcribed` 是关键行的逐字转写。
- **② 问题定位**：指到 `file` / `line` / `symbol`，`reason` 要写"图内证据 ↔ 代码片段"的对应关系，`confidence < 0.5` 时界面提示补信息。
- **③ 解决方案**：可执行 `steps`、最小 `patch`、`verification` 勾选项，**外加 `boundaries`（这个方案在什么情况下不成立）** —— 这一条是刻意加的，避免给出"看起来能跑但换个环境就炸"的答案。

### 4.3 提示词策略

- 三段顺序固定，先文字后图片（模型对"图前文字"的指令遵循度更高）；
- 按场景注入清单：代码要读报错行与缩进、表格要读行列头与合计、图表要读坐标轴单位；
- 代码与图的绑定规则：要求模型先在图里找与代码同名的符号，再定位；
- `buildJsonRepairPrompt` 只修格式，不重解问题（避免"修格式把结论改了"）。

## 5. 适用边界（这些情况它一定不行）

1. **规则分类不理解语义**。它只看排版信号：把 PDF 里的表格截图和真表格、把 Markdown 表格和纯文字都按"有没有横竖线"判。所以合成样本 11/11 **不等于**真实准确率——真实基线要等 50 张人工标注评测集（P1-15）。
2. **极简卡片列表页会被判 `document`**。没有顶栏/侧栏的"一列卡片"和文档在特征上几乎同构（实测合成界面图 → `document`）。缓解：两者都按文字类编码（PNG）、清单高度重合，`ui` 与 `document` 只差长边上限 1440/1600。
3. **深色终端里的红字会判 `code` 而不是 `error`**。两类清单都含"读报错行"，实务上可接受。
4. **暖色渐变的置信度低**。日落/暖光照片现在判 `photo`，但 `margin` 只有 0.026（`uncertain = true`），界面会提示可手动改类——它长得确实像示意图。
5. **HEIC / TIFF / SVG 能不能解，取决于浏览器**。判不出来会走中文友好报错（"这个格式当前浏览器解不了，请截图或转 PNG"），不会静默失败。
6. **裁剪有下限**。只裁 `document/table/chart`，且要求检测框 ≥35% 面积、每边 ≥40%。所以"留白超过 65% 的极端页面"不会被裁——宁可多送白，也不冒误裁风险。
7. **体积阶梯最多 6 次尝试**。极端图（如 16bit 超大 PNG）仍可能 `overBudget`，此时照送并在界面标注，不阻断流程。
8. **模型仍可能读错**，`coverage.missing` / `status=partial` 就是给这种情况准备的信号；`structured=false` 时界面自动切成纯文本视图。
9. **客户端不做 OCR**。逐字转写由模型完成，细小文字（原图 <7px 行高）即使 2× 放大也未必读得出，`too_small_text` 会提前提示。

## 6. 验收标准（可直接执行）

```bash
# 1. 类型（web 严格模式）
npm --prefix web run typecheck

# 2. 单测：1193 条，0 失败
node qa/run-tests.mjs

# 3. 分类标定：11 个样本全部命中（terminal-red 允许 code|error）
npx tsx qa/vision-probe.ts

# 4. 性能：4K 特征 ≤25ms（实测 21.12ms）、4K 预处理提速 ≥5×（实测 7.75×）
npx tsx qa/vision-bench.ts

# 5. 真实编码：3 例全 ok，单张 ≤1.5MB（实测 738KB / 44KB / 97KB）
node qa/vision-browser-probe.mjs
```

| 指标 | 阈值 | 实测 |
| --- | --- | --- |
| 特征 + 哈希 + 分类（4K） | p95 < 100 ms | 36.24 ms |
| 预处理提速（4K vs 旧版） | ≥5× | 7.75× |
| 单张送入体积 | ≤1.5 MB | 最大 738 KB |
| 整批送入体积（5 张） | ≤4 MB | 预算按张数分摊 |
| 分类合成样本 | 11/11 | 11/11 |
| 解析健壮性 | 永不抛错 | 单测覆盖脏 JSON / 缺字段 / 纯文本 |
| 体积阶梯 | ≤6 次且像素单调 | 单测覆盖 |

> 探针实现说明：`vision-browser-probe.mjs` 用 **CDP**（`--remote-debugging-port=0` + `DevToolsActivePort` + `Runtime.evaluate` 轮询）而不是 `--dump-dom`。原因：`--virtual-time-budget` 靠虚拟时钟推进，页面在跑 12MP 噪点/4K 编码时虚拟时钟会提前耗完，dump 出来还是 `PENDING`；而且虚拟时间会让 `performance.now()` 失真，耗时可采信度为零。
